# 11/8 직접 사용 — 진행 기록

## Pleos 부팅 직후 앱 표시 위치 어긋남

사용자가 앱이 오른쪽으로 밀려 내용과 버튼이 잘리는 화면을 제보했다. 실제 캡처에서도 재현했다. View 접근성 좌표와 WindowManager의 앱 영역은 `[853,90][2535,1300]` 안으로 정상 보고됐으나, 화면 픽셀은 그보다 오른쪽·아래로 밀려 있었다. 따라서 앱의 고정 여백 문제로 단정하거나 음수 여백으로 보정하지 않았다.

이번 실행에서는 에뮬레이터 `sys.boot_completed=1` 직후 앱을 먼저 열었고, 이후 Pleos 홈·차량 화면이 분할 영역을 구성했다. 그 전환과 관련된 렌더링 위치 문제로 추정한다. 정확한 원인과 반복 재현 조건은 아직 확정하지 않았다.

- 복구: 차량 홈이 준비된 상태에서 앱 프로세스만 종료하고 다시 실행. 데이터 삭제·앱 재설치·제품 코드 변경 없음.
- 확인: 홈 전체가 앱 영역에 표시됨. 화면상의 기록 버튼 위치를 실제 탭하여 입력 화면이 열리고 확인/취소 버튼이 모두 보이는 것 확인. 빈 초안 취소 후 홈으로 복귀.
- 추가 확인: Pleos 홈으로 이동했다가 MAIN/LAUNCHER 경로로 재진입해도 정상 표시.
- 날짜: Pleos 부팅 과정에서 시간대가 America/Los_Angeles로 바뀌는 것도 확인. 개발 에뮬레이터 시간대를 Asia/Seoul로 맞췄다. 저장한 지출은 없음.
- 제한: 이번 조치는 정상 표시로 복구한 것이며, 냉간 부팅·분할 전환의 재발 방지를 검증한 영구 수정은 아니다. 제출용 영상 촬영과 release 검증 전에 안정된 차량 홈에서 시작하는 절차와 냉간 시작을 다시 확인해야 한다.

증거: `artifacts/usability-2026-11-08/`의 before/relaunch/form/home-return 실제 캡처, UI hierarchy 및 WindowManager 덤프.

이 복구 시점에는 민수의 지출 입력·수정·삭제·재실행 직접 사용 확인이 진행 전이었다. 아래 후속 확인과 구분한다.

## 입력칸 선택 시 전체 화면 키보드

사용자가 입력칸 선택 시 앱을 가리는 큰 입력 영역과 키보드를 제보했다. `dumpsys input_method`에서 선택된 입력기는 `ai.umos.inputmethod/.service.CarIME`, `mIsFullscreen=true`, `mExtractViewHidden=false`로 확인했다. 차계부 화면이 아니라 Pleos 입력기의 전체 화면 편집 모드다. 화면의 마이크 아이콘 또한 해당 입력기의 UI이며 앱의 오프라인 음성 엔진과 연결된 버튼이 아니다.

- 현재 상태: 문장·금액 입력칸에 전체 화면 입력 방지 설정이 없음. 입력기 전체 화면 동작을 줄이는 설정 적용과 실제 키보드·스크롤 검증이 보완 항목이다. 아직 수정·재설치하지 않았으며 사용자의 입력 중 초안은 건드리지 않았다.
- 사용자 확인용 대안: 뒤로가기로 키보드를 닫고 앱의 `주유 7만원` 예시 버튼으로 금액·항목 확인 및 저장 흐름을 확인할 수 있다.
- 음성 상태: 제품 기록 화면의 실제 마이크 연결은 미구현. 별도 진단 화면의 합성 음성 처리·마이크 해제 검사와 실제 사용자 발화 정확도 검증은 구분한다. 키보드 마이크의 동작 여부는 이번에 시험하지 않았다.

## 사용자 입력·저장 확인과 예시 버튼 의견

민수가 직접 사용한 뒤 “입력은 잘되는 것 같다”고 확인했다. 제공한 화면에는 2026.11.08 주유 70,000원과 7,000원 두 건, 합계 77,000원, 주유 비중 100%가 표시된다. 화면상 내역·건수·합계·비율은 일치한다. 각 기록의 입력 방식과 원래 의도한 금액까지 이 캡처로 추정하지 않는다. 수정·삭제·재실행 보관의 사용자 확인은 아직 남아 있다.

사용성 의견: 직접 입력이 귀찮아 사용자가 예시 버튼을 주로 누를 것 같다는 피드백. 현재의 전체 화면 키보드와 문장 입력 부담이 드러났으며, 고정 예시 금액을 실제 지출로 저장할 가능성도 고려해야 한다. 다수 사용자의 행동으로 일반화한 검증 결과는 아니다.

설계 제안: Phase 3에서는 말하기를 주 행동으로 두고 금액·항목 확인 후 저장한다. 현재 예시는 사용법 안내로 축소하거나 주 입력 영역에서 제외하는 방향을 검토한다. 반복 입력 편의는 필요성이 확인되면 사용자가 실제 저장한 최근 내역을 기반으로 별도 검토하되, 이번에 즐겨찾기·추천 기능 구현을 확정한 것은 아니다. 실제 발화로 입력 부담이 줄어드는지는 연결 후 확인한다.

## 삭제 확인 팝업 확대 — 구현·검증 완료

사용자 제보: 삭제창과 문구·버튼이 너무 작음. 기본 AlertDialog를 그대로 사용해 차량용 화면의 글자·버튼 크기와 맞지 않았다.

- 삭제와 입력 취소 확인창을 공통 처리. 앱 창 너비를 기준으로 최대 960dp, 내용에 맞는 높이, 공통 폰트·텍스트 역할·색상·모서리 적용. 확인을 눌렀을 때의 저장/삭제 로직은 유지.
- Pleos 기본 글씨에서 팝업 실제 크기 768×180 → 960×305px. 취소·삭제 버튼은 각각 200×80px이며 이 AVD의 밀도는 160dpi이다. 제목 40sp, 본문·버튼 25sp(넓은 창 배율 반영).
- debug 앱·테스트 APK 빌드, lint 성공. 최초 컴파일의 접근성 heading 속성명 오류를 고친 뒤 성공한 산출물을 설치했다.
- LedgerFlowTest 1개 통과: 기존 저장·수정·초안 복원·취소·삭제 흐름과 추가한 삭제 취소 시 기록 유지 검사 포함.
- 기본 화면과 야간/fontScale 1.3 조합의 실제 삭제 팝업 캡처 확인. 시스템 전환 중 앱이 가려져 다시 진입한 뒤 확인했으며 설정은 낮 모드·1.0으로 복원.
- 작업 전후 DB 행을 비교해 기존 기록이 모두 같은 상태로 유지됨을 확인. 테스트가 만든 임시 기록만 정리했다. 사용자 기록을 대신 삭제하지 않았고, 수정된 삭제 팝업을 열어 두었다.
- 근거: `artifacts/usability-2026-11-08/delete-dialog-{light,dark-large}.{png,xml}`. 휴대폰 좁은 창·실차는 이번 검사 범위 밖이다.


## 수정 폼·확인 팝업 재정리 — 11/8 후속

사용자가 토스 입력 화면과 Material 팝업을 참고한 개선 방향을 승인했다. 이전 팝업 확대 기록은 위에 보존하고, 현재 구현은 아래 기준으로 대체한다.

- 수정 화면 전체를 최대 960dp로 제한해 앱 영역 가운데 배치. 제목·날짜·폼·안내의 왼쪽 기준선을 통일했다. 중복 소제목을 제거하고 라벨을 Regular/보조색으로 낮춰 금액을 강조했다. IBM Plex Sans KR과 홈 대시보드는 유지했다.
- 취소는 중립색, 저장은 파란색으로 한 줄에 배치. 실제 버튼 영역이 `560dp × fontScale`보다 좁으면 세로로 재배치하며, 클릭 영역 최소 높이 64/80dp와 내용에 맞는 높이를 유지한다. 삭제는 구분선 아래의 별도 텍스트 버튼이다.
- 삭제·입력 취소는 native AlertDialog 안에 공통 레이아웃을 사용한다. 최대 880dp, 내부 여백 32dp, 제목→본문 16dp, 본문→버튼 32dp. 전체 내용은 스크롤 가능하다. 낮은 elevation과 배경 dim으로 구분하고, 삭제 확정 버튼에는 error/on_error 대비색을 적용했다. 삭제 안내는 저장된 원본을 지우는 동작과 맞게 일반 문구를 사용하며, 저장하지 않은 수정 금액을 삭제 대상으로 표시하지 않는다.
- 앱·테스트 APK 빌드 및 lint 성공. 커스텀 팝업 설정 시 Builder가 아닌 AlertDialog.setView 오버로드를 사용하도록 최초 컴파일 오류를 수정했다. LedgerFlowTest 1개 통과(3.306초): 신규 저장, 중복 방지, 금액 검증, 초안 복원, 수정, 입력 취소, 삭제 취소 및 확정 포함.
- Pleos 2.1 / API34 / 2560×1440, 앱 영역 1682×1210에서 실제 수정 폼·삭제 팝업을 확인했다. 낮/fontScale 1.0 및 야간/fontScale 1.3에서 금액·안내·행동이 잘리지 않았다. Activity configuration에서 1.3 적용을 확인했고 낮/1.0으로 복원했다.
- 독립 레이아웃 검토에서 추가 결함 없음. layout detector 전후 결과 `[]`이나 Kotlin의 시각적 완성도를 보증하는 검사는 아니며 실제 렌더와 함께 판단했다.
- 작업 전후 DB 모든 행의 동등성을 확인했다. 사용자의 2건 기록은 변경하지 않았다.
- 근거: `artifacts/usability-2026-11-08/{edit,dialog}-refined-{light,dark-large}.{png,xml}`, `form-refinement-build.log`, `form-refinement-flow.txt`. 실차 검증은 하지 않았다. 마이크 및 전체 화면 CarIME 개선은 이번 범위 밖이다.

참고: [Toss TextField](https://tossmini-docs.toss.im/tds-mobile/components/TextField/text-field/), [Material Dialog](https://m3.material.io/components/dialogs/overview), [Google 차량 타이포그래피](https://developers.google.com/cars/design/automotive-os/design-system/typography). 웹 컴포넌트나 라이브러리를 가져오지 않고, 현재 Android Views에서 배치 원칙을 적용했다.

- 좁은 화면 추가 검증: 별도 Medium Phone API36.1 AVD를 시작했으나 스트리밍 설치와 파일 전송 후 설치 모두 완료 응답이 지연됐다. UI dump도 null root/I/O 오류로 유효한 렌더를 얻지 못해, 휴대폰 검증을 통과로 표시하지 않는다. 이번에 시작한 테스트 AVD만 종료했고 사용 중인 Pleos는 유지했다.

## 사용자 삭제 확인 — 11/8 후속

사용자가 “팝업 괜찮은 것 같고 삭제 기능도 잘 된다”고 직접 확인했다. 팝업 디자인과 삭제 동작의 사용자 확인으로 기록한다. 삭제한 기록의 ID·금액·잔여 합계는 이번 발언만으로 추정하지 않는다. 수정 결과·재실행 보관·월 이동·입력 취소까지 모두 직접 확인했다고 확대 해석하지 않는다.

## 사용자 수정·취소·월 이동 확인 — 11/8 후속

사용자가 수정 후 저장이 정상 동작했고, 새 기록 입력 중 취소했을 때 금액 변동이 없었으며, 11월에서 12월로 이동했을 때 합계가 정상 표시됐다고 직접 확인했다. 구체적인 수정 금액이나 월별 합계는 이번 발언에서 제공되지 않아 추정하지 않는다. 앱 종료 후 재실행은 아직 해보지 않았다고 명시했으므로 사용자 확인 미완료로 유지한다. 자동 테스트의 재실행 보관 검증과 구분한다.

- 실행 중 PID 13966 확인 → `am force-stop --user 10 com.iancompany.voiceledger` → pidof 결과 없음으로 종료 확인 → MAIN/LAUNCHER 진입으로 재실행. `LaunchState: COLD`, 새 PID 29662 확인.

- 이것은 앱 프로세스 종료·재실행 검증이며, 차량/에뮬레이터 재부팅이나 Pleos 초기 분할 전환 문제 검증은 아니다. 사용자가 직접 한 확인과 구분해 Codex 수행으로 기록한다.
