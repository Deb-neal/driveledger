## 1. 앱 한 줄 소개

**차 안에서 잊기 전에 말로 지출을 기록하고, 한 달 동안 내 차에 쓴 돈을 확인하는 차량용 음성 차계부.**

표현 후보: “차에서 한마디, 이번 달 차 비용이 보인다.”

## 2. 기획 배경

주유·주차·정비 비용은 차량을 이용하는 과정에서 발생하지만, 운전자는 나중에 가계부에 입력하려다 잊기 쉽다. 전체 카드 청구액만으로는 차량 때문에 발생한 지출이 얼마인지 구별하기 어렵다. 여러 카드나 현금으로 나눠 결제하면 별도 정리도 필요하다.

사용자는 실제로 가계부에 기록해야겠다고 생각하다가 귀가 후 잊은 경험을 공유했다. 이것은 문제 발견의 근거이며, 전체 운전자의 수요나 절약 효과를 입증한 조사 결과는 아니다.

이 앱은 비용이 발생한 직후 차 안에서 짧게 말해 기록을 끝내고, 월별 차량 지출과 항목별 내역을 보여준다. 사용자에게 제공하려는 가치는 기록 부담과 누락을 줄이는 것, 그리고 차량 비용을 구체적인 숫자로 이해하게 하는 것이다. 지출 인식이나 행동 변화 효과는 검증할 가설이다.

## 3. 타깃과 경쟁 대안

초기 타깃은 자가용으로 출퇴근하면서 차량 지출을 따로 알고 싶지만 가계부 기록을 미루거나 중단한 운전자다. 내연기관·전기차 모두 지출 기록 대상이며, 주유와 충전은 별도 분류한다.

기존 대안은 일반 가계부, 마이현대 차계부, 전문 차량 관리 앱이다. 마이현대는 이미 주유 소비내역·정비 내역·연비 통계를 제공하고, Drivvo도 차량 비용과 정비를 관리한다. 차계부 자체나 음성 입력을 세계 최초라고 주장하지 않는다.

차별화 가설은 **지출 직후 차량 안에서 짧게 입력하고, 현재 차량 주행거리와 연결한 뒤, 월별 비용 확인까지 이어지는 경험**이다. 스마트폰 음성 입력도 경쟁 대안에 포함하여 실행·입력·확인까지의 전체 과정을 비교한다. 단순히 같은 화면을 차량 디스플레이에 옮기는 것으로 차량특화성이 확보된다고 보지 않는다.

## 4. 주요 기능과 차량 특화 요소

### 1차 제출 MVP — 반드시 동작시킬 범위

| 기능 | 사용자 경험 | 완료 기준 |
| --- | --- | --- |
| 음성 기록 | 마이크 버튼 → “오늘 주유 7만 원” → 짧은 확인 → 저장 | 실제 마이크 입력으로 금액·항목을 추출하고 확인 후 기록 |
| 수정·취소 | 안전하게 주차한 상태에서 화면의 수정/취소 버튼 | 잘못된 금액은 저장 전 수정 가능, 중복 저장 방지. 음성 수정 대화는 후속 확장 |
| 차량 주행거리 연결 | 입력 시점의 지원되는 누적 주행거리를 기록에 첨부 | 실제 SDK 값과 출처·조회 시각 기록, 미지원은 공란 처리 |
| 월별 차량 지출 | “이번 달 기록된 차량 지출” 합계와 항목별 내역 | 저장·수정·삭제가 합계에 정확히 반영 |
| 기록 조회·편집 | 날짜·항목·금액 확인, 잘못된 기록 수정 | 앱 재실행 후 유지, 다른 달의 지출은 해당 월에 반영 |
| 실패 대응 | 인식 실패 시 재시도, 정차 중 간단한 수동 입력 | 실패·취소된 음성은 자동 저장하지 않음 |

1차 문장 지원 범위는 오늘의 단일 지출 금액·항목이다. 항목이 불명확하면 선택하지 않은 상태로, 금액이 불명확하면 빈칸으로 남겨 직접 확인한다. 여러 항목이나 금액을 말하면 한 건씩 다시 입력하도록 안내한다. 과거 날짜·메모·음성 수정 대화는 후속 확장으로 두며, 자유로운 자동차 상담이나 모든 자연어 표현 처리를 약속하지 않는다.

주유·충전·주차·통행료는 운행 관련 지출, 정비·보험·자동차세는 유지·보유 관련 지출로 묶어 볼 수 있게 한다. 기타/미분류도 허용한다. 차량 구입·대출·할부의 원금 및 이자 분석은 MVP에서 제외한다.

### 화면과 사용 맥락

- 홈: 마이크 진입, 이번 달 기록된 차량 지출, 최근 기록.
- 입력 확인: 인식 문장, 금액·항목·날짜, 기록 당시 주행거리, 저장·수정·취소.
- 월별 내역: 항목별 합계와 기록 목록. 정차 중 상세 편집.
- 최초 사용: 차량 표시명과 간단한 기록 안내. MVP는 한 기기·한 차량·로컬 저장을 기본으로 하며 로그인은 요구하지 않는 안이다.
- 대표 사용 장소는 주유·정비를 마친 후 안전하게 주차한 차 안이다. 신호 대기는 정차 사용 시나리오로 취급하지 않는다.
- 주행 중 상세 표·키보드·편집을 제한하고 플랫폼의 주행 규제를 적용한다. 음성 입력의 주행 중 허용 여부는 정책 확인 후 결정하며 초기 시연은 주차 상태에서 진행한다.
- 시동 시 자동 실행, 주유 감지 팝업, 상시 마이크, 깨우기 단어는 MVP의 전제에 넣지 않는다. 실제 앱 진입부터 기록 완료까지의 조작 수를 측정한다.

## 5. 주요 사용 시나리오

### A. 주유 직후 기록

1. 출퇴근 운전자가 주유 후 주차된 차 안에서 앱을 연다.
2. 마이크를 누르고 “오늘 주유 7만 원”이라고 말한다.
3. 앱은 오늘 날짜·주유·70,000원과 현재 조회한 주행거리를 보여준다.
4. “주유 7만 원, 기록할까요?”라는 짧은 확인 후 사용자가 저장한다.
5. 실제로 저장된 기록이 목록과 이번 달 합계에 반영된다.

### B. 잘못 들은 금액 수정

“주차비 4천 원” 이후 “아니, 4천5백 원”이라고 수정한다. 앱은 확인 중인 한 건의 금액만 바꾸며, 두 지출로 중복 저장하지 않는다. 저장 후 수정은 해당 기록을 선택해 처리한다.

### C. 정비비와 교체 메모

“엔진오일이랑 필터 교체, 총 12만 원”을 정비 120,000원과 메모로 저장한다. 비용별 분할이나 차종별 교체 주기 계산은 수행하지 않는다. 기록 당시 주행거리가 있으면 이후 정비 이력을 확인하는 데 활용할 수 있다.

### D. 월별 비용 확인

앱에서 이번 달을 선택해 기록된 지출과 항목별 합계를 확인한다. 시연용 예시: 주유 24만 원 + 주차 8만 원 + 통행료 5만 원 + 정비 8만 원 = 45만 원. 이 값은 실제 사용자 데이터가 아니며 화면·영상에서 예시 데이터임을 표시한다. “이번 달 얼마 썼어?” 음성 조회는 핵심 기록 기능 완료 후 추가할 선택 기능이다.

## 6. 숫자와 데이터의 의미

- 합계는 **기록된 차량 지출**이다. 누락된 결제까지 포함한 실제 총비용이나 전체 카드 청구액이라고 표현하지 않는다.
- KRW 정수 금액으로 저장·합산하고, LLM에게 합계를 계산하게 하지 않는다.
- 지출 발생일과 입력일을 구분한다. “어제”는 한국 시간 기준으로 해석하고 사용자 확인을 받는다.
- 과거 지출을 입력할 때 현재 조회한 주행거리를 과거 교체 당시 거리로 붙이지 않는다. 당시 거리를 모르면 미상으로 둔다.
- 주유 결제액은 해당 월의 현금 지출 성격의 기록이며, 그 달 실제로 소비한 연료의 비용과 동일하지 않다. 주유비를 주행거리로 나눈 수치를 정밀한 연료비/km라고 주장하지 않는다.
- 카드 사용 건과 카드 대금 납부를 이중 합산하지 않는다. MVP는 개별 차량 지출만 기록한다.
- 보험료·세금 등은 발생한 달의 실제 지출로 표시한다. 월할 환산 예상 부담은 후속 기능이며 실제 지출 합계와 분리한다.
- 기본 저장 필드: 기록 ID, 발생일, 입력 시각, 금액, 항목, 메모, 선택적 주행거리와 조회 시각·출처, 입력 방식. 통화는 원화로 고정한다.
- 음성은 기본적으로 영구 저장하지 않는 설계다. 외부 음성/LLM 서비스를 쓰면 전송 범위를 표시하고 필요한 데이터만 보낸다. 외부 API 비밀 키를 APK나 공개 저장소에 넣지 않는다.

## 7. 개발 계획과 기술 선택

Kotlin 기반 Android 앱으로 구성한다. 화면은 Compose, 상태는 ViewModel/StateFlow, 기록은 로컬 DB를 사용하는 안이다. 구체 라이브러리 버전은 Phase 1에서 호환 조합을 검증하여 고정한다.

- 공식 최소 조건: minSdk 28 이상, Gradle 8.0 이상, Java 또는 Kotlin.
- 현재 확인한 환경: Pleos Connect Emulator 2.1.0 / 시스템 이미지 API 34, Vehicle SDK 2.3.2, STT/TTS 각각 3.3.1.
- API 28은 minSdk 하한이다. compileSdk·targetSdk 및 AGP·JDK·Kotlin 조합은 따로 확인한다.
- 차량 데이터는 읽기 전용으로 사용한다. Odometer 조회의 권한·capability·초기화·해제·지원 상태를 검증한다.
- 음성 인식 → 필드 추출 → 검증 → 확인 → 로컬 저장 → 결정적 집계로 분리한다.
- Phase 1에서 Pleos STT/TTS의 실제 마이크 경로를 먼저 검증한다. 실패 시 지원되는 대체 경로의 정책·통신·비용 조건을 확인하며, 어떤 방식이든 실제 음성 입력이 동작해야 음성 MVP 완료로 본다.
- 흔한 금액·항목 표현은 제한된 규칙으로 시작할 수 있다. 자유 발화 처리에 LLM이 필요하면 정해진 필드만 반환하게 하고, 서버 구성과 사용 비용을 포함해 도입 여부를 결정한다. LLM 채택 자체는 MVP 완료 기준이 아니다.
- Gleo Interface는 향후 앱 호출 통합 후보로 둔다. 첫 제출을 Gleo 승인에 의존시키지 않는다. 기존 Pleos LLM SDK는 2026-10-19 릴리즈에서 제공 종료로 명시되었다.
- 실제 카드 승인·하이패스 요금·정비소 결제 내역을 Vehicle SDK에서 자동으로 받을 수 있다는 근거는 확보하지 않았다. 자동 수집을 구현 기능으로 쓰지 않는다.

## 8. 범위 우선순위

| 구분 | 내용 |
| --- | --- |
| 1차 필수 | 실제 음성 기록, 확인·수정·취소, 로컬 보관, 월별·항목별 합계, 지원되는 주행거리 연결, 실패 대응, release APK |
| 여유가 있을 때 | 정해진 문장의 음성 월별 조회, CSV 내보내기, 간단한 전월 비교 |
| 1차 이후 검토 | Gleo 앱 호출, 휴대폰 동기화, 사용자별 기록, 정비 이력 활용, 연간 비용·월평균 부담 |
| 별도 근거·연동 필요 | 카드/하이패스/영수증 자동 수집, 정비 상담, 보험·정비 제휴, 법인 비용 정산 |

음악 추천·낮잠 제어·브레이크 마모 예측은 이번 제품 범위에 포함하지 않는다. 1차 이후 기능도 모두 구현하기로 약속한 것이 아니다.

| 차량특화성 | 지출 직후 차량 안에서 기록하고 주행거리와 연결 | 앱 진입부터 저장까지 시연, 실제 SDK 값, 스마트폰 방식 대비 조작·시간 비교 | 휴대폰 음성 입력보다 편한지 아직 미검증 |
| 창의성 | 기록을 미루다 잊는 순간을 해결하고 차량 비용 이해로 연결 | 사용자 경험 인터뷰와 기록 누락 변화 | 차계부 자체는 기존 서비스이며 새롭다고 주장하지 않음 |
| 기술 활용성 | STT/TTS와 차량 데이터를 기록 과정에 직접 활용 | 마이크 입력·수정·Odometer·저장·집계가 이어지는 실행 영상 | 사용 권한과 실제 기기 동작 미검증 |
| 사업성 | 기록 부담 때문에 중단한 출퇴근 운전자의 반복 사용 | 초기 유입 경로, 기록·조회 활성화, D7 재방문 및 후속 D30 계획 | 지불 의사와 장기 유지율 미검증 |

선택 산출물 가산점은 위 네 항목을 대체하지 않는다. 비공개 배점을 임의로 추정하지 않는다.

## 10. 사용자 검증과 사업성 가설

### 작은 검증

- 10/28~30: 사용자 본인과 참여 가능한 운전자 3~5명에게 실제 기록 누락 경험, 사용하는 앱, 차량 비용을 확인하려는 이유를 묻는다. 모집·연락은 사용자가 진행하거나 별도로 지시한다.
- 11/5~8: 실제 음성 버전이 준비되면 주차 상태에서 동일한 가상 지출 6건을 스마트폰 기존 방식과 차량 음성 방식으로 기록한다. 순서를 바꿔 학습 효과를 줄인다.
- 시간은 앱을 여는 시점부터 최종 저장까지 잰다. 소요 시간·조작 수·정확 저장률·수정 횟수와 월별 비용 이해도를 함께 기록한다.
- 일부 참여자가 며칠간 사용하면 발생한 지출 대비 실제 기록 여부를 본인 확인으로 조사한다. 모든 결제를 수집하지 못하므로 기록 누락률을 정확히 자동 측정했다고 표현하지 않는다.
- 설계 목표는 흔한 한 건 기록을 15초 안에 완료하는 것이다. 달성된 성능이 아니며 측정 결과로 갱신한다.
- 소수 테스트 결과를 전체 시장 효과로 일반화하지 않는다. 1차 마감 전에 장기 유지율이나 절약률을 실측했다고 주장하지 않는다.

### 확보·지속 이용·확장

초기 확보 경로는 사용자 주변 운전자와 허용된 차량 커뮤니티의 소규모 체험 모집을 가정한다. Pleos App Market 노출·입점·배포는 보장되지 않으며 실제 배포 승인 전제의 미래 계획이다. 특정 커뮤니티에 글을 게시하거나 참가자를 모집한 상태가 아니다.

가입/설치보다 실제 기록과 월별 조회를 활성 행동으로 본다. 한 달에 1회 이상 기록 저장 또는 월별 리포트를 조회한 고유 사용자를 MAU로 정의한다. D7 유지율은 첫 기록 사용자 중 7일째 기록 또는 리포트 조회로 돌아온 비율로 정의하고, 모집단·표본 수를 함께 표기한다. D30은 1차 제출 이후 추적한다. 최초 MVP는 로컬 저장이므로 참여자 동의하에 테스트 로그·설문으로 검증하고 자동 원격 분석을 이미 구축했다고 쓰지 않는다.

예상 MAU는 실측 전이며 공개 배포 후 3개월 차의 민감도 예시만 둔다. 해당 월 방문자 500명 × 설치 전환 20% × 설치자 월간 활성 50% = 신규 유입 활성 사용자 50명이다. 기존 설치자의 재방문은 데이터가 없어 계산에서 제외했다. 수치는 시장 근거가 없는 작업 가정으로, 지원서 제출 전 실제 확보 경로와 테스트 결과로 대체하거나 '가정에 따른 추정'으로 명시한다. 유지율 목표 역시 사용자 테스트 후 정하며 숫자를 실적처럼 쓰지 않는다.

반복 사용의 가설은 지출 직후의 짧은 기록과 월말 비용 확인이다. 수익화는 기본 기록 제공 후 상세 리포트·내보내기·공유 등에서 지불 의사를 조사하는 후속 과제다. 소비 감소·가계 절약 또는 유료 전환을 보장하지 않는다.

## 11. 참고자료와 제출 시 상태

현재 제공 가능한 자료는 이 기획 초안과 일정 문서뿐이다. 앱 화면·영상·GitHub·APK는 개발 후 실제 결과로 채운다. 참가자 정보·서명은 공식 양식의 운영용 영역에 별도로 작성하고, 작품 소개와 첨부자료에 개인 정보나 계정 비밀이 노출되지 않도록 확인한다.

공식 양식의 1~6번에 대응하는 내용은 위 소개·배경·기능·시나리오·개발·기대효과 절을 편집해 옮긴다. 계획 기능과 구현 완료 기능을 제출 시 다시 구분한다. 7번 참고자료에는 검증된 링크만 넣고, 8번 숏폼은 필수 산출물 이후 여유가 있을 때 판단한다.
