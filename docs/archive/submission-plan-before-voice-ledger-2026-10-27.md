## 개발 환경 필수 조건 — 2026-10-27 재확인

제품 후보와 관계없이 적용할 개발 조건이다. 아직 프로젝트 생성·SDK 설치·빌드·실행은 하지 않았다.

- 최소 API 28은 문서상 차량 사이버 보안 요건(사이닝 키 로테이션·리니지 지원)에 따른 필수 조건이다. 이 값만 충족했다고 모든 서명·등록 요건이 충족되는 것은 아니다.
- 기존 개발 환경 페이지는 검색 결과에 과거 SDK 버전이 남아 있지만 직접 열면 Page Not Found였다. 현재 설치 가이드와 2026-10-19 SDK 릴리즈 노트를 기준으로 확인했다. 검색 요약의 버전을 그대로 복사하지 않는다.
- 2026-10-19 에뮬레이터 릴리즈 노트에 **LLM SDK 제공 종료**가 명시되어 있다. 기존 Pleos LLM SDK를 사용할 수 있다고 가정하지 않는다.
- Gleo Interface는 별도 문서로 제공되며 앱 스키마와 function calling을 통해 앱과 연동한다. 정비 도우미에서 사용할 수 있는 함수 범위·등록 절차·에뮬레이터 검증 가능 여부는 미확인이다. LLM SDK 종료를 Gleo 종료로 해석하지 않는다.
- 음성 질의응답은 Gleo Interface 연동 또는 별도 LLM 연결을 검토하되, 방식은 아직 확정하지 않았다. 정비 시기 계산은 차량별 기준과 이력에 기반한 로직으로 분리한다.
- Phase 1 착수 시: 도구·SDK 버전 기록 → 호환 조합 확정 → 최소 앱 빌드 → Pleos 에뮬레이터 설치·실행 확인을 선행 완료 기준으로 삼는다. 기능 구현 범위는 제품 방향 확정 후 다시 작성한다.

## 서류 평가 기준과 현재 정비 도우미 후보의 검증 과제

사용자가 공유한 공식 평가 문구를 기준으로 정리했다. 차량특화성·창의성·기술 활용성·사업성은 모두 필수 평가이며 세부 배점은 비공개다. 특정 항목의 비중이 더 높다고 가정하거나 임의의 합산 점수를 만들지 않는다. 개발 산출물은 선택 가산점이며 필수 평가항목을 대체하지 않는다.

현재 정비 도우미는 구현 범위를 잡기 좋은 주력 검토 후보지만, 심사 경쟁력이 검증된 최종안은 아니다. 아래 설계는 제안이며 구현된 기능이나 확보된 데이터가 아니다.

| 평가항목 | 현재 후보의 약점 | 기획·시연에서 입증할 내용 |
| --- | --- | --- |
| 차량특화성 | 정비 주기 알림과 일반 지식 질의응답은 모바일에서도 가능 | 지원되는 차량 주행거리와 정비 이력에 근거한 알림, 정차·주행에 맞는 정보량과 조작 방식. 차량 안에서 쓰면 어떤 단계가 줄어드는지 모바일 방식과 비교 |
| 창의성 | 기존 관리 기능에 LLM을 추가하는 것만으로는 독창성이 부족 | 운전자가 알림을 이해하지 못하거나 이력을 누락한 실제 사례, 알림 근거 설명→이력 확인·수정→알림 재계산이 기존 대안보다 나은지 검증 |
| 기술 활용성 | SDK 이름만 나열하거나 Fake 데이터만 보여주면 활용 증거가 약함 | 실제 지원·권한이 확인된 주행거리 등 차량 데이터가 핵심 판단을 바꾸는 장면. STT/TTS 또는 Gleo 연동은 별도 가능성 검증. 실제 SDK 입력과 시뮬레이션을 명확히 표시 |
| 사업성 | 정비는 매일 발생하지 않아 매일 접속할 이유와 개인 구독 의사가 불명확 | 정비 지식이 부족한 출퇴근 운전자라는 타깃 가설 검증, 구체적 확보 경로와 유입 가정, 월간 재방문 및 다음 정비 시점 재사용 등 사용 주기에 맞는 지표 |

- 핵심 시연 후보: 주행거리/이력 기반 알림 → 사용자의 “왜 지금?” 질문 → 차량별 기준과 해당 기록 설명 → 누락된 교체 이력 확인·수정 → 알림 재계산. 실제 액 상태나 패드 마모를 측정했다고 주장하지 않는다.
- 시동 시 자동 실행·팝업, 주행 중 음성 동작, 정비 이력 자동 연동은 플랫폼 정책·데이터 접근을 검증하기 전 확정 기능으로 적지 않는다.
- MAU는 확보 가능한 유입 모수·활성화율 등의 가정을 명시한 시나리오로 작성한다. Retention Rate는 코호트·기간·재사용 행동을 정의한다. 목표·예상·소규모 검증 결과와 실측을 구별한다.
- 알림 클릭률, 질문 후 이해도, 정비 기록 완료율은 사용자 가치의 보조 지표다. 이를 Retention Rate와 혼동하지 않는다. 정비 완료는 확인된 경우에만 집계한다.
- 1차: 동작 범위를 정확히 드러내는 프로토타입 영상, GitHub 소스와 실행 가능한 release APK를 목표로 한다. 산출물에 따른 가산점의 세부 수치는 추정하지 않는다.
- 2차 PT 전 실제 동작 앱 완성이 필요하며, 1차 제출 이후 고도화할 수 있다. 확장 기능은 필수 핵심 경험의 완성을 밀어내지 않도록 분리한다.
- 다음 기획 판단: 사용자 불편과 차량에서의 이점이 확인되지 않으면 LLM 기능을 늘리기 전에 후보 자체를 재검토한다.

## 2. 현재의 기획 방향

### 해결할 문제 — 검증 전 가설

음악을 들으며 혼자 운전하는 사람이 주행 분위기가 달라질 때마다 음악을 다시 고르는 번거로움을 느낀다. 차량 상황을 이용해 음악 경험을 자연스럽게 이어주면 조작 부담을 줄이고 만족도를 높일 수 있다는 가설이다. 효과가 입증되었다고 주장하지 않는다.

### 타깃과 첫 사용 장면

- 초기 타깃: 음악을 들으며 혼자 퇴근하거나 저녁 드라이브를 하는 운전자.
- 대표 여정: 저녁 주행 → 와이퍼 지속 작동 → 밤으로 전환 → 비 오는 밤의 음악 경험.
- 핵심 약속: 사용자가 선택한 분위기를 바탕으로 차량 상황에 맞게 자연스럽게 이어지는 음악.
- 전조등만으로 밤을, 와이퍼만으로 강수량을, 크루즈만으로 장거리 주행을 단정하지 않는다.
- 지원하지 않거나 받을 수 없는 신호는 정상적인 OFF와 구분한다.

### 10/29에 결정할 두 구현 후보

| 후보 | 핵심 경험 | 채택 조건 | 범위 영향 |
| --- | --- | --- | --- |
| A. 기존 상황별 추천 | 현재 곡 유지, 다음 곡부터 목록 전환 | 추천의 유용성·차별성을 설명할 수 있고, 실제 재생 또는 시연용임을 명확히 한 경험을 준비할 수 있음 | 기존 Phase 구성 유지 |
| B. 차량 반응형 사운드트랙 | 같은 멜로디의 레이어를 상황에 맞게 변화 | 직접 제작 또는 사용권 확보가 가능한 오디오, 두 상황 간 자연스러운 변화, 반복 재생 안정성 확인 | Phase 2의 Playlist/Playback 명세 수정 필요 |

B는 제안일 뿐 채택되지 않았다. 가짜 재생기는 실제 음원 경험을 입증하지 못한다. B를 선택해도 실시간 AI 작곡·상용 스트리밍 연동·대규모 음악 카탈로그는 이번 MVP에 포함하지 않는 방향을 권장한다.

### 작은 검증 계획

- 사용자 본인 또는 모집한 운전자 3~5명에게 최근 음악을 바꾸었던 실제 상황, 번거로움, 자동 변경을 원치 않는 순간을 묻는다. 모집·연락은 사용자가 수행하거나 별도 지시한다.
- 음악 후보를 비교할 때는 같은 기본 음원으로 일반/비 오는 밤의 30초 샘플을 비교한다. 아직 샘플을 제작한 것은 아니다.
- 기록할 것: 사용자가 이해한 가치, 변화의 자연스러움, 다시 사용할 이유, 거부 이유. 소수 의견을 시장 전체의 검증으로 표현하지 않는다.
- 10/29 결정 기준: 문제의 공감도, 30초 안의 차별성 전달, 음원 확보 가능성, 제출일까지의 구현 가능성. 둘 다 약하면 1일 이내 타깃·시나리오를 재정의하고 기능 범위를 줄인다.

## 3. 1차 제출 목표와 범위

목표 패키지: 서명한 기획서 + 핵심 경험의 시연 영상 + 소스 코드와 설치 가능한 release APK.

- Phase 1의 순수 Kotlin 로직과 Fake 신호 모델은 원래 명세대로 설계·검증한다.
- 첫 화면과 시연은 기본/비/밤/비 오는 밤에 집중한다. 동승자·스포츠·크루즈 등 확장 상황의 UI 및 오디오 콘텐츠는 핵심 경험보다 뒤에 둔다.
- 실제 SDK 통합은 와이퍼부터 시작하고 지원이 확인된 신호를 추가한다. 실제 SDK 반응을 최소 하나 보여주는 것을 내부 목표로 삼는다.
- 시연에는 Fake 신호인지 SDK에서 받은 신호인지 표시한다. 가상 재생을 실제 음악 재생처럼 표현하지 않는다.
- 미지원·연결 실패 시 기존 안정 상태 또는 기본 상태를 유지하고 오류를 관찰할 수 있게 한다.
- 신규 AI 서버, 로그인, 결제, 음악 취향 학습 모델, 모든 무드별 대규모 콘텐츠 제작은 1차 범위에서 제외하는 안이다.

## 5. 일정 지연 시 판단 기준

- 10/28~29: 현재 컴퓨터에서 Pleos 에뮬레이터를 실행할 수 있는지 조기에 확인한다. 실행 환경 확보를 Phase 3까지 미루지 않는다. 호환 환경이 없으면 가능한 별도 PC 확보 또는 공식 지원 환경 확인을 우선한다.
- 10/29: 오디오를 확보하지 못했거나 변화가 부자연스러우면 B를 강행하지 않는다. A를 택하더라도 실제 재생과 시뮬레이션의 구분을 유지한다.
- 11/6: 핵심 여정이 동작하지 않으면 추가 무드·부가 UI·시각 효과를 줄이고 기본/비/밤의 흐름에 집중한다.
- 11/9: SDK 연동이 불안정하면 지원 확인된 한 신호부터 안정화한다. 미완료 부분을 공개하고 Fake 시연과 혼동하지 않도록 한다. 1차 산출물은 선택 제출이라는 점을 활용하되 실제 동작을 과장하지 않는다.
- 11/11: 신규 기능은 종료한다. 빌드·설치·문서·영상 품질에 집중한다.
- 하루 1~2시간만 가능하면 핵심 여정 한 개의 프로토타입과 기획서를 우선하며, 동일한 전체 범위가 가능하다고 가정하지 않는다.
