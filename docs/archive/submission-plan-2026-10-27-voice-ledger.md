# 음성 차계부 — 개발 및 제출 일정 v0.1

기준일: 2026-10-27 / Asia/Seoul(KST)
제품 방향: 차 안에서 말로 지출을 기록하고 월별 차량 비용을 확인하는 앱. 앱 이름은 미정이다.
상태: 기획·일정 작성 완료, 개발 미착수. [기획 초안](product-brief.md)이 기능 범위의 기준이다.
작업량 가정: 1인·하루 3~4시간. 실제 투입 시간과 팀 구성은 미확인이다. 10/27~11/13의 18일은 약 54~72시간이며, 여유가 큰 일정은 아니다.

## 1. 공식 일정과 내부 목표

| 날짜 | 공식 일정 | 내부 대응 |
| --- | --- | --- |
| 2026/10/21~11/15 | 1차 접수 | 첨부 접수양식 기준 11/15(일) 23:59 KST 마감 |
| 10/28(수) 오후 | 온라인 설명회 | 확인 시각 기준 정확한 시간·접속 방법은 추후 안내 상태 |

접수는 appdevchallenge@hyundai-partners.com 이메일이며 접수양식 자체가 기획서다. 1차 영상·GitHub(소스+APK)는 선택 가산점이고, 2차 PT 전 실제 동작 앱 완성이 필요하다. 1차 제출 이후 고도화할 수 있다. 세부 배점은 공개되지 않았다.

공식 GitHub 안내의 “제출 페이지 입력” 문구와 이메일 접수 절차가 함께 있으므로 별도 페이지 입력 필요 여부를 설명회에서 확인한다. 이 문서 작성만으로 이메일 발송·저장소 공개·예약·알림 자동화를 실행한 것은 아니다.

## 2. 이번에 완성할 한 가지 흐름

**주차한 차 안에서 앱 열기 → 마이크 → “오늘 주유 7만 원” → 날짜·금액·항목·지원되는 현재 주행거리 확인 → 저장 → 이번 달 기록된 차량 지출에 반영.**

금액 수정, 취소, 재실행 후 보관, 월별·항목별 집계를 포함한다. 앱 진입과 확인 과정도 편의성 측정에 포함한다. 시연용 기록과 실제 기록, 실제 SDK 값과 Fake 값을 구분한다.

카드·하이패스 결제 자동 수집, Gleo 통합, 정비 상담, 마모 예측, 로그인·휴대폰 동기화, 상시 마이크는 1차 필수 범위에 포함하지 않는다. 선택 기능은 핵심 기록 흐름을 완성한 뒤에만 진행한다.

## 3. 단계별 일정

각 Phase를 순서대로 진행하고 완료 시 결과·테스트·남은 문제를 보고한 뒤 다음 단계 착수 전 멈춘다. 사용자의 기존 단계별 진행 요청을 유지한다. 이번 요청은 초안·일정 작성이므로 구현은 시작하지 않는다. 검토 지연이나 SDK 접근 지연이 생기면 날짜를 재조정한다.

| --- | --- | --- | --- |

## 4. Phase 1에서 먼저 해결할 사항

- 공식 필수 조건: minSdk 28 이상, Gradle 8.0 이상, Java/Kotlin 중 Kotlin.
- 현재 확인한 버전: Emulator 2.1.0 / 시스템 이미지 API 34, Vehicle SDK 2.3.2, STT/TTS 3.3.1. API 28과 실행 이미지 API 34를 혼동하지 않는다.
- Gradle Wrapper·AGP·JDK·Kotlin·compileSdk·targetSdk는 지원 문서와 실제 SDK 요구를 대조해 하나의 호환 조합으로 고정하고 기록한다. 아직 이 조합을 설치·검증하지 않았다.
- Mac용 ARM64 이미지가 공식 안내에 있으나 현재 호스트에서 실행된다는 검증은 아직 없다.
- SDK 사용 신청·권한·실제 의존성 접근, 에뮬레이터의 마이크 전달, STT 결과·TTS 출력, Odometer capability·조회·생명주기를 작은 실험으로 확인한다.
- 화면의 정차/주행 제약을 플랫폼 규제 상태와 연결하는 방법을 확인한다. 미확인 상태를 무조건 주차 상태로 취급하지 않는다.
- 기존 Pleos LLM SDK는 제공 종료다. Gleo Interface 또는 외부 LLM을 바로 쓸 수 있다고 가정하지 않는다. MVP의 제한된 지출 문장은 규칙 기반 해석부터 평가할 수 있다.
- 음성 공급자 경로는 10/30까지 정한다. 외부 API가 필요하면 서비스 접근·전송 범위·백엔드·키 관리·비용을 포함한 범위를 다시 산정한다. 키를 APK에 넣는 방식으로 시간을 줄이지 않는다.
- Phase 1 완료 보고에 실제 동작 화면, 사용 버전, 성공·실패한 SDK 기능, 다음 단계의 확정 범위를 남긴다. 접근 실패만 확인한 상태라면 “연동 완료”로 보고하지 않는다.

## 5. 중요한 검증과 일정 조정 기준

| 시점 | 확인할 문제 | 대응 |
| --- | --- | --- |
| 10/30 | 에뮬레이터 또는 음성 입력 경로 미확보 | 10/31 작업 초반에 지원 가능한 대체 경로를 확인하고 일정 재산정. 소프트웨어 모형만 동작하면 실제 음성 구현과 구분 |
| 11/3 | 기록·집계 정확성 또는 보관 문제 | 선택 기능을 제거하고 저장·수정·합계부터 해결 |
| 11/6 | 음성으로 한 건 기록하는 전체 흐름 미동작 | 자연어 지원 범위를 단일 금액·항목으로 축소. 월별 음성 질의·전월 비교·CSV 제외 |
| 11/8 | SDK 주행거리 조회 불가 | 원인·미지원 상태를 표시하고 수동/미상으로 기록 가능하게 유지. 차량특화성 입증이 약해진다는 점을 제출물에 반영 |
| 11/11 | 실행 가능한 release 미확보 | 신규 기능 중단, 설치·서명·오류 해결 우선. 선택 산출물을 제출 가능한 수준으로 조정하고 미완료 기능 명시 |

가짜 마이크 입력을 실제 음성처럼 시연하거나 Fake 주행거리를 실제 차량 데이터로 표현하지 않는다. 시연 영상은 목업도 인정되지만, 실행 APK 제출 시에는 실제 기능과 제약을 정확히 설명한다.

기능 테스트는 금액·날짜·집계·중복 저장·과거 지출의 주행거리 오연결에 집중한다. 음성·오디오 포커스·권한·네트워크·주행 규제·앱 재시작은 에뮬레이터에서 실제 동작으로 확인한다. 기능 변경 없이 같은 테스트를 반복 확대하지 않는다.

하루 1~2시간만 가능하면 이 계획의 전체 범위를 유지할 수 있다고 가정하지 않는다. 음성 한 건 기록·월 합계·최소 SDK 연동에 집중하고 제출 가산점 산출물 수준을 조정한다. 협업자가 생기면 디자인·사용자 검증·제출 자료를 분담하고 앱 기능 수는 늘리지 않는 편을 우선한다.

## 6. 기획서와 사용자 검증도 개발과 함께 진행

- 10/28~30: 실제 기록 누락 경험과 차량 지출을 따로 알고 싶은 이유 조사. 기존 차계부와 스마트폰 음성 입력의 전체 단계를 비교한다.
- 11/3: 실제 화면으로 공식 양식 1~5번 문장을 갱신한다.
- 11/5~8: 가능한 참여자 3~5명의 비교 테스트. 앱 진입부터 저장까지 시간·조작·정확도·수정 횟수를 기록한다.
- 11/9~12: 확보된 초기 재사용 결과를 정리한다. D7이 경과한 참여자만 해당 지표에 포함하고, 부족하면 관찰 일수와 실제 표본 수를 적는다. D30·절약 효과는 미래 검증 계획으로 표시한다.
- 예상 MAU는 확보 경로·전환 가정을 공개한 추정으로 작성하고, 근거 없는 숫자를 실적처럼 쓰지 않는다.
- 네 필수 평가항목 각각에 사용자 경험·실제 기능·검증 자료가 연결되도록 작성한다. LLM 사용 여부나 기능 개수로 창의성을 대신 설명하지 않는다.

## 7. 시연 영상 구성 — 내부 제안 60~90초

1. “기록하려다 집에 가면 잊는다”는 상황과 앱의 한 줄 가치.
2. 주차 상태의 앱 실행부터 실제 마이크로 주유비 입력.
3. 금액 수정, 짧은 확인, 지원되는 차량 주행거리와 함께 저장.
4. 월별 항목 합계와 이번 달 기록된 차량 지출 확인.
5. 실제 동작 범위·에뮬레이터 사용·예시 데이터 여부 표시.

60~90초는 제작 목표이며 공식 영상 길이 제한으로 확인한 값이 아니다. 예시 45만 원을 만드는 사전 기록은 데모 데이터로 표시하고 실제 사용자의 한 달 결과처럼 소개하지 않는다.

## 8. 제출 확인

- 공식 양식: 참가 정보, 작품 소개, 참가자 전원 동의·본인 서명·날짜. 작품 소개와 공유 자료의 개인정보·계정정보·개발자 실명 노출 확인.
- 기획서: 타깃, 실제 불편, 모바일 대비 이점, SDK 활용, 기존 서비스와 차이, 확보·유지·확장 가정. 구현 완료와 계획 구분.
- GitHub: 소스와 `apk/팀명_앱이름_release.apk`. 실제 실행 가능한 release로 제출. 용량 초과 시 GitHub Releases 페이지 링크.
- README: 앱 이름·소개, 실행 방법, 테스트 환경·필요 설정, APK 경로 또는 Release 링크, Fake/실제 SDK 구분, 알려진 제약.
- APK: 제출할 서명본의 설치·실행 검증. 개발용 비밀 키·서명 키·실사용 지출 데이터는 저장소에 넣지 않음.
- Private 저장소: 공지된 심사 계정 초대와 제출 마감 전 접근 확인. 개인 저장소 collaborator의 쓰기 권한도 확인.
- 이메일 제목: `[차량용 앱 개발 공모전] 팀명(개인은 성명)_대표자명`. 팀이면 전원 CC. 제출은 사용자가 실행하거나 별도로 지시한다.
- 수정 제출: 같은 발신자에서 전체 자료와 서명 동의서를 다시 제출, 제목에 `[수정제출]` 추가. 마지막 제출본이 최종본이다.
- 숏폼은 별도 특별상으로 본상 가산점이 없다. 핵심 산출물 이후 판단한다.

## 9. 10/28 설명회 확인 목록

1. 정차/주행 중 마이크·STT·TTS 사용 정책과 오디오 포커스 요구는 무엇인가?
2. STT/TTS와 Odometer 사용 신청·권한·에뮬레이터 제약은 무엇인가?

5. GitHub 별도 제출 페이지 입력 필요 여부와 Private 심사 계정은 무엇인가?
